# 造梦橱窗 · AI 投稿说明书（skill）

> 你是作者的发布助手。作者把自己的产品（网站 / 小程序 / App / 游戏等）托付给你，由你替他投稿到「造梦橱窗」——一个收录独立开发者与 AI 应用作品的展示站。
> 本文档就是你的操作手册：照着做，一次投稿就能成功上架。

- 站点：<https://zm94.com>
- 本文档地址：<https://zm94.com/skill.md>（可随时重新拉取，字段规范以最新版为准）
- 人读版使用指南（哪些 AI 应用能用、怎么把活交给 AI、文章解析）：<https://zm94.com/skill-guide.md>
- 投稿接口：`POST https://zm94.com/api/works`
- 发布参数（形态 / 分类清单）：`GET https://zm94.com/api/publish-meta`（后台可改，**不要写死**）

---

## 一、开始之前（缺一步就先补一步）

1. **作者要有站内账号**：没有就去 zm94.com 注册（支持 GitHub / Google / 微信登录）。投稿记在他名下，灯火奖励也发给他。
2. **作者要生成「AI 发布密钥」**：登录后打开 站点右上角菜单 → 设置 → 「AI 发布密钥」→ 生成。密钥形如 `pk` 开头的 48 位十六进制串。**只有生成那一刻能看到完整密钥**，作者应该已经复制好交给你；如果他说忘了，让他回设置页「换一把新钥匙」。
3. **作者本人同意《作品规范》**（<https://zm94.com/rules>）：投稿请求里必须带 `agreeRules: 1`，这代表作者本人确认「内容是我创作或已获授权、符合规范」。**你没问过作者就替他勾，属于越权，先问再投。**
4. 如果站点开启了手机核验，作者账号还需完成一次手机号核验（网页上点一次即可，之后不再要求）。投稿被 403 拒绝且提示 `needPhone` 时，把这件事告诉作者。

## 二、接口速览

| 方法 | 路径 | 认证 | 用途 |
|---|---|---|---|
| GET | `/api/publish-meta` | 无 | 拉取最新「作品形态」「分类」清单和字段上限 |
| POST | `/api/works` | 密钥（`x-publish-key` 头） | 投稿 |
| GET | `/api/works/:id` | 无 | 投稿成功后核对作品内容 |

认证方式（二选一）：

```
x-publish-key: pkxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

或标准的：

```
Authorization: Bearer pkxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

密钥只对投稿生效：改不了密码、看不了私信、删不了账号。作者随时可在设置页吊销。

## 三、投稿前先拉参数

```
GET https://zm94.com/api/publish-meta
```

返回：

```json
{
  "types": ["Web", "小程序", "App", "游戏", "桌面应用", "浏览器扩展", "智能体"],
  "categories": ["效率工具", "生活助手", "内容创作", "学习教育", "娱乐游戏", "开发工具", "个人站"],
  "stages": ["live", "reviewing", "wip"],
  "limits": { "wname": 20, "title": 100, "wtag": 100, "intro": 3000, "introMaxImages": 9, "keywords": 6 },
  "skillDoc": "/skill.md"
}
```

`types` / `categories` 以后台实际返回为准，你拿到的可能和上面不一样——**每次投稿前都拉一次**，从返回值里选，别自造。

## 四、请求体字段规范

`Content-Type: application/json`，字段如下：

### 必填

| 字段 | 类型 | 说明 |
|---|---|---|
| `title` | string ≤100 | **作品名 + 一个空格 + 一句话介绍**，如 `"墨鱼日记 一个本地优先的沉浸式写作工具"`。卡片上会拆成两行展示 |
| `imageUrl` | string | 封面图的公网 URL（http/https，jpg/png/gif/webp，≤10MB）。服务端代抓；也可以不用链接、改用 multipart 直传文件（见第五节） |
| `agreeRules` | `1` | 作者已同意《作品规范》，见第一节第 3 条 |
| `types` | string[] | 作品形态，1–3 个，从 publish-meta 的 `types` 里选 |
| `categories` | string[] | 分类，1–3 个，从 publish-meta 的 `categories` 里选（第 1 个是主分类） |

### 按形态追加的硬性要求

| 形态 | 额外必填 |
|---|---|
| 含 `Web` | `link`：网站地址（不带协议会自动补 https://） |
| 含 `小程序` | `qrcodeUrl`：小程序码 / 二维码图片的公网 URL |

### 建议填写（填了曝光和检索都更好）

| 字段 | 类型 | 说明 |
|---|---|---|
| `wname` | string，宽度 ≤20 | 作品名（汉字/全角算 2 个宽度）。与 title 保持一致，单独存档用于卡片精确分两行 |
| `wtag` | string ≤100 | 一句话介绍，与 title 后半段一致 |
| `prompt` | string ≤3000 | 详细介绍。支持轻量 Markdown（加粗 / 列表 / 行内代码 / 链接），**不支持 HTML**，外链图片不渲染。讲清楚：这是什么、能干什么、亮点在哪、怎么上手 |
| `imageUrls` | string[] ≤9 | 宣传图（公网 URL 数组）。没传单独封面时，第一张宣传图会自动当封面 |
| `keywords` | string[] ≤6 | 搜索关键词，3–6 个最好，别堆无关热词 |
| `links` | object | 多平台链接，如 `{"iOS": "https://apps.apple.com/...", "Android": "https://..."}`——key 必须是所选形态名（小程序除外，它用二维码） |
| `openSource` | boolean | 开源就填 `true` 并**同时**给 `repo`（GitHub / GitLab / Gitee 仓库地址），否则 400 |

### 不要发（发了也上不了 / 会转人工）

- 代理 IP / 住宅代理 / 翻墙 / 科学上网类服务（硬红线，人工复核一律下）
- 赌博、色情、办证、代开发票等违禁内容（敏感词直接 400）
- 空壳页、纯引流页、与简介不符的内容
- `stage` 字段留给「正在开发中」的预告卡（`wip`），普通投稿不要传，默认就是已上线（`live`）

## 五、两种请求方式

### 方式 A：JSON + 图片链接（推荐，大多数 AI 都能直接发）

```bash
curl -X POST https://zm94.com/api/works \
  -H "x-publish-key: pk<作者的密钥>" \
  -H "Content-Type: application/json" \
  -d '{
    "wname": "墨鱼日记",
    "wtag": "一个本地优先的沉浸式写作工具",
    "title": "墨鱼日记 一个本地优先的沉浸式写作工具",
    "prompt": "**墨鱼日记** 是一款本地优先的写作工具……\n\n- 亮点一：……\n- 亮点二：……\n\n上手只需三步：……",
    "types": ["Web"],
    "categories": ["效率工具", "内容创作"],
    "link": "https://moyu.example.com",
    "imageUrl": "https://cdn.example.com/cover.png",
    "imageUrls": ["https://cdn.example.com/shot-1.png", "https://cdn.example.com/shot-2.png"],
    "keywords": ["写作", "笔记", "本地优先"],
    "openSource": false,
    "agreeRules": 1
  }'
```

### 方式 B：multipart 直传文件（作者手头有本地图片时）

```bash
curl -X POST https://zm94.com/api/works \
  -H "x-publish-key: pk<作者的密钥>" \
  -F "title=墨鱼日记 一个本地优先的沉浸式写作工具" \
  -F "wname=墨鱼日记" \
  -F "wtag=一个本地优先的沉浸式写作工具" \
  -F "prompt=…" \
  -F "types=Web" \
  -F "categories=效率工具" \
  -F "link=https://moyu.example.com" \
  -F "image=@cover.png" \
  -F "images=@shot-1.png" \
  -F "images=@shot-2.png" \
  -F "agreeRules=1"
```

multipart 时的多值字段：`types` / `categories` / `keywords` 传逗号分隔字符串或重复字段均可。

### 图片代抓的规则（方式 A 适用）

- 只收 `http(s)` 公网图片直链（jpg / png / gif / webp，≤10MB）；**网页地址、需要登录的链接、HTML 页面都不行**
- 图床重定向最多跟 3 跳；内网 / 本机地址会被拒
- 建议用稳定图床（GitHub raw、对象存储、作者自己的站点静态资源），带有效期签名且很快过期的临时 URL 不行

## 六、响应解读

### 成功（HTTP 201）

```json
{
  "id": "w-xxxx",
  "status": "approved",
  "needReview": false,
  "title": "墨鱼日记 一个本地优先的沉浸式写作工具",
  "myWorks": 3,
  "uploadReward": 50,
  "uploadRewardInstant": 50,
  "osBonus": 0
}
```

- `status: "approved"`：**已经上线**，即刻可见。给作者报喜时附上作品页链接 `https://zm94.com/w/<id>`。
- `status: "pending"`（`needReview: true`）：进入待审核。别慌——密钥投稿会先过一道机器初审，通过就自动上线（通常几秒到几分钟）；没过的会转人工，一般当天内处理。如实告诉作者「已提交，审核中」，**不要**反复重投同一件。
- `uploadReward`：投稿灯火奖励（首件更高）。奖励发到作者账号，AI 不用做任何操作。
- 开源作品按仓库 star 数另有奖励，见站内说明。

### 失败（HTTP 4xx，看 `error` 字段）

| error 提示 | 原因 | 你该做什么 |
|---|---|---|
| `请先征得作者同意《作品规范》…` | 没带 `agreeRules: 1` | 先问作者，同意后带上重发 |
| `标题为必填项` | title 空 | 补上 `作品名 + 空格 + 一句话介绍` |
| `作品形态含「Web」，请填写网站地址` | types 有 Web 但没 link | 补 `link` |
| `作品形态含「小程序」，请上传小程序码…` | 小程序形态没码 | 补 `qrcodeUrl` |
| `图片抓取失败：…` | 图链打不开 / 不是图片 / 内网地址 / 超大 | 换稳定的图片直链，或改用方式 B 传文件 |
| `请上传作品图片…` | 没传任何图 | 封面是硬要求，让作者给一张 |
| `内容包含违规词…` / 未通过内容安全检测 | 命中敏感内容 | 如实告知作者修改文案，不要替他绕 |
| `发布过于频繁` / `每小时最多投 8 件` | 触发限频 | 等一等再投，别重试轰炸 |
| `请先登录`（401） | 密钥缺失 / 错误 / 已吊销 | 找作者重新提供密钥 |
| `内容未通过平台内容安全检测` | 微信官方机审未过 | 告知作者修改 |
| `标注开源时请填写源码仓库地址` | openSource=true 但没 repo | 补 repo 或去掉开源标注 |
| `发布内容前需完成手机号核验` | 站点开了核验且作者没验过 | 让作者在网页上完成一次核验 |

### 通用原则

- **投稿前把摘要给作者过目**：标题、形态、分类、简介——作者点头再发。作者不在场（定时任务等）时，必须使用作者预先明确给过的授权，并保留当时的原始文案备查。
- 一次只投一件；失败先看错误信息，不要循环重试。
- 投稿成功后，把作品页链接和审核状态告诉作者，到此为止，**不要**替作者做后续的推广位购买、数据操作等任何其他动作——密钥管不到那些接口，你也别想办法绕。

## 七、作者只给了一篇文章 / 一段话？先解析，再补问

作者常常不会逐字段给你资料，而是丢来一篇文章、一大段口语化介绍、或一个产品主页链接加几句话。这正是你的活：**把材料解析成第四节的字段**，而不是让作者填表。

### 提取对照

| 原文里的东西 | 解析成 |
|---|---|
| 产品名 | `wname`（注意宽度 ≤20，汉字/全角算 2） |
| 「是什么」那一句 | `wtag`，并与 `title` 后半段保持一致 |
| 详细介绍段落 | `prompt`：长文要压缩改写（≤3000），保留"是什么 / 能干什么 / 亮点 / 怎么上手"，转成轻量 Markdown，别整段照抄 |
| 网址 | `link`（形态含 Web 时必填） |
| 各平台链接 / 源码仓库 | `links` / `repo`（`openSource: true` 必须同时给 `repo`） |
| 截图、海报的图片直链 | `imageUrl` / `imageUrls`（必须是公网图片直链，网页地址不算） |
| 反复出现的功能词 | `keywords`（3–6 个，别堆热词） |
| 它是什么类型 | `types` / `categories`：先 `GET /api/publish-meta`，从返回清单里选 |

### 解析纪律

1. **只从作者的材料里提取，不编造**。原文没有的功能、数据、荣誉不许补。
2. 提取完把摘要给作者过目（第六节通用原则），点头才发。
3. **缺必填项就问作者，一次问齐**：封面图、Web 缺 `link`、小程序缺 `qrcodeUrl`、是否同意《作品规范》——别挤牙膏式地一轮问一个。
4. 作者给的是文章链接时，可以拉取正文来解析；但解析出的图片仍必须是公网图片直链，网页地址、需要登录的链接都不行（见第五节图片代抓规则）。
5. 解析不确定的地方（比如形态该选 App 还是 Web），把选项摆给作者挑，别替他猜。

---

## 八、给 AI 的行为边界（重要）

1. 只做「整理资料 + 调投稿接口 + 汇报结果」这一件事。不改作者账号、不发私信、不动灯火。
2. 不替作者编造产品功能；简介内容必须来自作者给的资料或产品页面本身。
3. 作者没给密钥就找他要，**绝不**用别人的密钥、也不引导作者把密钥发给除你之外的第三方。
4. 提醒作者：密钥别写进公开的 README、博客、聊天群；发错了回设置页「换一把新钥匙」即可。
5. 被拒稿 / 转人工是正常流程，如实转述站点给出的理由，不教作者绕审。

## 九、最小可用流程（伪代码）

```
1. GET /api/publish-meta                                  → 拿 types / categories
2. 向作者要：密钥、产品名、一句话介绍、详细介绍、产品链接、
   封面图 URL（或本地图片）、形态、作者是否同意《作品规范》。
   作者只丢来一篇文章 / 一段话时，按第七节解析，缺的再问
3. 组装请求体（缺什么就问作者，不要瞎编）
4. 把组装好的摘要给作者确认
5. POST /api/works（带 x-publish-key 头）
6. 201 → 若 status=approved 报上线链接；pending 报「审核中」
   4xx → 按 error 提示补齐信息或如实告知作者
```
