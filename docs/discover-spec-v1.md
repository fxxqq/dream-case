# 首页「随便逛逛」分层随机推荐 · 方案定稿 v1

最后更新：2026-11-09

---

## 0. 一页结论

| 项 | 结论 |
|---|---|
| 模块定位 | 首页新增一段「随便逛逛」，只负责「偶遇」和均匀曝光，不参与任何榜单 |
| 计数口径 | `n` = 这件作品被**多少个不同的人**在模块里看到（累计，只增不减） |
| 排队 | 按 `n` 升序分桶，最小桶优先；桶内加权（`k=0.3`，纯随机 `k=0`） |
| 重复防护 | 每个访客一份「已推过」名单，推过的永不重复推（180 天） |
| 池空的定义 | 不再是「额度用完」，而是「这个人把全站看完了」→ 空状态 + 三个出口 |
| 砍掉的东西 | 上限 10、滚动 30 天窗口、30 天统一重置、兜底弹窗 |

**为什么砍**：原方案用「0→9 梯队 + 上限 10」手工模拟了一个更简单的机制——「永远优先推曝光最少的那批」。那个硬上限本身制造了「池子会空」这个伪问题：80 件 × 10 = 800 个名额，一屏 12 张，约 67 次首页浏览就耗尽，模块上线两三天后永久变成一条引导条。去掉上限，「池子空」就不存在了。

## 1. 名词与口径（先统一，避免各端各算）

| 名词 | 定义 | 实现 |
|---|---|---|
| 一次有效曝光 | 卡片在可视区内面积 ≥ 50% 且持续 ≥ 500ms | IntersectionObserver |
| 曝光人数 `n` | 该作品被多少个不同的**人**曝光过 | `works[id].s.length` |
| 认人 | 登录 `u:<uid>` / 小程序 `d:<deviceId>` / 网页·H5·App `v:<dm_vid>` | 复用 `visitorId()` 三端统一 |
| 推过 | 该访客在模块里见过这件作品的卡片 | `users[vid].ids`，保留 180 天 |
| 详情点击 | 从模块卡片进入详情页 | 单独字段 `c`，**不改 `n`** |

> 「人」而不是「次」是关键：次数口径有一个 DoS 面——刷别人的作品曝光，就能把它顶出池子。人数口径同一台设备看 50 次也只算 1 个名额。

## 2. 数据结构

`data/expo.json`（debounced 落盘，和 `share.json` 同一套路）

```json
{
  "ver": 1,
  "works": {
    "w_abc123": {
      "s": ["v:9f2a", "v:1b7c"],
      "c": ["v:9f2a"],
      "at": 1762650000000
    }
  },
  "users": {
    "v:9f2a": { "ids": ["w_abc123"], "at": 1762650000000 }
  },
  "manual": {
    "w_abc123": { "lv": 2, "until": 1763860000000 }
  }
}
```

- `s`：曝光过的访客 id，去重，**存储封顶 60**（`n < 30` 时绝不截断，所以 `n` 精确）。这是纯存储优化，与业务无关——`n ≥ 30` 时作品已离开优先池，记第 61 个人对取卡没有任何用处
- `c`：其中点进过详情的访客，去重，上限 60。**恒有 `c ⊆ s`**，保证 CTR 分子分母同口径
- `users[vid].ids`：这个人在模块里被推过的作品 id，上限 200（LRU），180 天不活跃即清理
- `manual`：管理员手动加权，`until` 到期自动失效
- 体积估算：80 件 × 60 × 12B ≈ 57KB + 用户侧（500 人 × 80 × 10B ≈ 400KB），可接受

不存「次数 + 日桶」的理由：不需要滑窗了，日桶反而多一层聚合逻辑。

## 3. 接口契约

### 3.1 曝光上报（批量）

```
POST /api/track
{ "action": "expo", "ids": ["w_a", "w_b"], "vid": "v:9f2a" }
```

- 一屏多张卡由前端 300ms 合并成一次请求，不要 12 个并发
- 服务端逐件处理：作品可见 && `vid ∉ s` && `s.length < 60` → push
- 幂等：同一 vid 重复上报不增长
- 返回 `{ ok: true }`；单件失败不影响其它
- 限频：沿用 `/api/track` 现有 900 次/小时/IP

### 3.2 点击上报

```
POST /api/track
{ "action": "expoClick", "workId": "w_a", "vid": "v:9f2a" }
```

- 仅在 `vid ∈ s` 且 `vid ∉ c` 时 push，保证 `c ⊆ s`
- **不动 `n`**，不消耗曝光名额（方案 A 敲定）

### 3.3 取卡

```
GET /api/discover?vid=<v:xxx>&size=12&mode=pool
```

```json
{
  "state": "full",
  "list": [ { "id": "w_a", "title": "...", "revisit": false } ],
  "total": 80,
  "left": 72
}
```

| state | 含义 | 前端 |
|---|---|---|
| `full` | 一屏全是没看过的 | 正常渲染 |
| `partial` | 没看过的排前，不够的用随机补，`revisit: true` | 补齐卡片打「重温」角标 |
| `empty` | 一件没看过的都没有了 | 渲染空状态（§6.4） |

- `size` 由前端按列数算出首屏可见张数传入，后端不感知列数
- 只有 `revisit: false` 的卡片写入 `users[vid].ids`

### 3.4 继续随机（洗牌发牌）

```
GET /api/discover?mode=random&vid=<v>&seed=<nonce>&page=1&size=12
```

- 种子 `mulberry32(hash(vid + seed))`，复用 `/api/featured` 里现成的 `mulberry32`
- 同一 seed 顺序稳定、翻页不重复（不会一屏里撞同一件两次）
- 刷新换 nonce 换顺序；服务端无状态

## 4. 取卡算法

```
pick(vid, size):
  seen = users[vid].ids
  # 2026-11-11 改口径：retired（n ≥ SOFT_RETIRE_N）不再踢出池子，改为排后垫底——
  # 拼在 pool 尾部，分桶按 n 升序天然排最后；只要本人没看过就不打 revisit 角标。
  # 原口径在小站会把「没逛过」掏空（曝光人数普遍过 30），清空已看也救不回来。
  pool = publicWorks() 过滤掉 seen；retired 件排尾部
  if pool 为空: return { state: 'empty', list: [] }

  buckets = groupBy(pool, w => n(w))
  out = []
  n = min(buckets.keys())
  while len(out) < size and n != null:
      take = min(size - len(out), len(buckets[n]))
      out += weightedSample(buckets[n], take, k)   # 无放回
      n = nextNonEmpty(n)

  if len(out) < size:
      out += randomFill(size - len(out), exclude=out)  # 打 revisit = true 后置顶到末尾
      state = 'partial'
  else:
      state = 'full'

  users[vid].ids += [w for w in out if not w.revisit]
  return { state, list: out }
```

**关于「不跨梯队」的修正**：原方案写「任何情况不允许跨梯队插队」，但一屏 12 张、最小桶只剩 5 个名额时物理上做不到。正确约束是：

- ✅ 允许**有序补齐**：按 `n` 升序一层层取，一屏可以跨层
- ❌ 不允许**跳层**：`n=3` 的作品不能排在还有 `n=1` 可推的情况下

实现上一个 `minN` 指针 + `Map<n, id[]>` 就够，不用枚举 0..9 十层。

## 5. 权重模型

```
w   = 1 + k × (pct − 0.5)        k = 0.3  →  w ∈ [0.85, 1.15]
pct = 该作品在本桶内的综合质量百分位（0 ~ 1）
```

**硬约束：权重只改顺序，不改入池。** 能不能进池只由 `n` 和 `seen` 决定。所以哪怕参数全错，公平性偏差上限也只有 ±15%。

| 信号 | 权重 | 公式 |
|---|---|---|
| CTR | 0.45 | `(|c| + α·G) / (|s| + α)`，`α=15`，`G` = 全站平均 CTR |
| 互动率 | 0.30 | `(赞 + 藏×1.5 + 评×2 + 送灯火人数) / max(|s|, 5)` |
| 管理员手动 | 0.15 | `(lv + 2) / 4`，`lv ∈ [−2, +2]`，到 `until` 失效 |
| 新鲜度 | 0.10 | 24h 内 = 1，否则 0 |

- 用**百分位**不用原始分：2000 star 的作品和 3 个赞的作品直接加权会把权重拉爆；百分位与量纲无关
- CTR 必须贝叶斯平滑：2 个人看到、1 个人点 → CTE 50%，不平滑会一直霸榜
- 互动用「率」不用「量」：`score()` 里的 赞5/藏8/评3/灯火10 是总量口径，会被历史累积碾压；除以曝光人数才是转化率
- 抽样用 **Efraimidis–Spirakis**：`key = rand() ** (1/w)`，取 key 最大的前 N 个。无放回一次出 N 张，不用「轮盘赌重抽」
- **只有 `k` 一个变量**：纯随机 `k=0`，优选 `k=0.3`。不要写 `if (mode === 'pure')` 两套分支，两条路径迟早不一致
- GitHub star 不进权重，只做勋章展示（站内有 star 的仓库极少，放进权重等于给固定账号长期微特权）

## 6. 前端

1. **位置**：首页「本周精选」下方，标题「随便逛逛」
2. **卡片**：复用现有 work-card；PC 4 列 / H5 2 列；`size` = 首屏可见张数（前端算，后端不感知）
3. **观测**：IntersectionObserver，可见面积 ≥50% 且持续 ≥500ms 才计；隐藏 tab / 预加载 / 快速滚过都不算
4. **空状态（内联，不弹窗）**：

   > 全站的作品你都看过了
   > `[随便翻翻]` `[去最新]` `[去看最热]`

5. **随便翻翻**：生成 nonce 存 sessionStorage，24h 内再进首页直接走 `mode=random`；点「去最新/最热」则跳对应 Tab，并清掉 nonce
6. **「重温」角标**：`partial` 状态下补齐的卡片右上角

不弹窗的理由：池子真的空了以后每次进首页都弹，只会逼用户点「继续」，等于训练用户无视弹窗。

## 8. 防刷

| 手段 | 说明 |
|---|---|
| UA / bot 闸 | 复用 `deviceOf`（headless 也拦） |
| 必须带 `vid` | 无 `vid` 直接丢弃，宁可少算不可错算 |

| 点击必须 ∈ `s` | 保证 CTR 分子分母同口径 |

## 10. 上线节奏与回滚

| 阶段 | 内容 | 观察 |
|---|---|---|
| 1（第 1 周） | 只做上报 + 后台看板，`DISCOVER_PICK=off`（模块不渲染） | 各作品曝光人数分布、真实 CTR |
| 2（第 2 周） | 开 `k=0` 纯随机分层 | 「一屏里同批作品连出」的频率 |
| 3（第 3 周） | 开 `k=0.3` | 分布偏移是否在 ±15% 内 |

没有第 1 周的数据，权重就是瞎猜——CTR 是第一权重维度，而现在它还不存在。

**回滚**：`DISCOVER_ENABLED=off` → 模块整段不渲染（不留空壳）；`k=0` → 立刻均等。

## 12. 需要点头的 3 个参数

1. **软上限**：`n ≥ 30` 的作品在池内排后垫底（2026-11-11 起，原先踢出池子、只在混填出现——小站曝光人数普遍过 30，会把「没逛过」掏空成 0~2 件）。建议 30；设 `999` 等于不降级
2. **加权强度** `k` 初值 `0.3` → 单件作品被抽中概率变化 ±15%
3. **保留期**：`seen` 180 天、每作品 `s` 上限 60

---

## 13. 一个必须知道的天花板

站内约 80 件作品，一屏 12 张 → **回头客 7 次浏览就把全站看完**。这不是算法问题，是内容量问题：这个模块对「新访客」有效，对「天天来的人」天然失效。空状态因此会很常见，视觉上必须做成「你已经逛完了」的语气，不能像报错页。想真正解决只能加内容。

## 14. 附录：性能测算（为什么上限不需要为性能让步）

**核心结论：上限值本身几乎不影响服务器压力。** 压力由「访客数」和「作品数」决定，不由这个数字决定。而且按「人数」计数天然自带限流——上限就是这件作品被多少个独立访客看过，不是可以无限增长的次数。

假设 80 件作品、日均 300 次首页浏览、一屏 12 张：

| 项目 | 量级 | 说明 |
|---|---|---|
| 曝光事件 / 天 | 3600 | 300 × 12 |
| HTTP 请求 / 天 | ~300 | 前端 300ms 合并，一次浏览只发一个请求 |
| 数组 push / 天 | 3600 | 每项仅一次 `Set` 查重 + 一次 push，微秒级 |
| JSON 落盘 | 数百次 / 天 | debounce 后写入，不是每次上报都落盘 |
| 取卡计算 | 每次排 80 件 | 纯内存，微秒级，不查库 |
| 文件体积 | works 侧固定 ~60KB | 唯一固定成本 |

与现有 `like-log.json` / `search-log.json` 同量级，CPU 与内存无压力。

**两个概念不要混淆：**

| | 是什么 | 值 | 不设的后果 |
|---|---|---|---|
| 业务上限 `SOFT_RETIRE_N` | 达到即在池内排后垫底（2026-11-11 起，不再离池） | 30 | 设 10 → 新作品排位被压（§0）；设过大 → 无降级信号 |
| 存储封顶 `S_CAP` | 第 N 个访客之后不再记入 `s` | 60 | 不设 → 热门作品永久存一长串 vid，纯浪费空间 |

`users[vid].ids` 是唯一会持续增长的部位：500 访客 × 80 件 × 10B ≈ 400KB，配合 180 天不活跃清理后稳定在 1.5MB 以内，同样不需要上限，只需要定期清理。
